# runtime-bun source — Bun reference runtime

## Overview
The Bun reference runtime composes kernel, durable store, runs, continuations, commitments, artifacts, and cognition behind `RuntimeService` (package description; [package.json:description]). `runtime.ts` is the composition root that opens the store, builds the Cordis kernel, the `Governor`, the `Invoker`, the continuation and artifact services, the projection runners, and the background loop [src/runtime.ts:startRuntime]. Run state is never a stored copy: it is a fold over the run stream, so payload erasure removes content from every derived view [src/fold.ts:foldRun].

## Interface
- `createRuntime(options)` — opens a `Runtime` from `RuntimeOptions` [src/index.ts:createRuntime]
- `Runtime` — `service`, `kernel`, `store`, `inspect(correlationId)`, `rebuildCognition()`, `erase(...)`, `pollApprovals()`, `idle(timeoutMs)`, `close()` [src/index.ts:Runtime]
- `RuntimeOptions` / `RuntimeStoreConfig` — store as SQLite path, injected store, `sqlite`, `postgres`, or `postgresPg0`; plus `policy`, `actions`, `agents`, `projections`, `execution`, `cognition` [src/index.ts:RuntimeOptions]
- `ActionPolicy` action names, `CognitionOptions`, `CausalChain`, `PendingEvent`, `OBSERVATION_OUTBOX_TOPIC` [src/index.ts:ActionPolicy, src/index.ts:OBSERVATION_OUTBOX_TOPIC]
- `Governor`, `validateGovernance`, `assertAuthorityClaims`, `isWorldRef`, `isSystemRead`, `parseTimeoutSeconds`, `timeoutSecsEnforcer`, `MAX_AUTHORITY_CLAIMS`, `MAX_AUTHORITY_CLAIM_LENGTH` [src/governed-operation.ts:Governor]
- `GovernanceOptions`, `GovernanceAuthority`, `GovernanceDecision`, `GovernanceConstraint`, `CapabilityHooks`, `Disposition`, `GovernedResult`, `ApprovalState` [src/governed-operation.ts:GovernanceOptions]
- `SeaForgeAuthority`, `buildAuthorityRequest`, `buildTransitionRequest`, `interpretDecision`, `interpretSettlement` and their receipt types [src/sea-forge-authority.ts:SeaForgeAuthority]
- `ENV_MODE`, `ENV_SOCKET`, `ENV_WORLD`, `ENV_ACTOR`, `governanceFromEnv(env)` [src/governance-env.ts:governanceFromEnv]
- Not exported: `Core`, `executeOnce`, `Invoker`, `ExecutionSlots`, `RemoteOfferRegistry`, `createService`, `inspectCorrelation` [src/core.ts:Core, src/executor.ts:executeOnce]

## Invariants
- Nothing outside `governed-operation.ts` may call `ActionPolicy.authorize` or the kernel `Policy`; only an `allow` disposition proceeds [src/governed-operation.ts:Governor]
- `sea-forge` mode without an authority and a valid `worldRef` fails at construction, and an unreachable authority yields `unknown`, never allow [src/governed-operation.ts:validateGovernance, src/governed-operation.ts:govern]
- A capability revalidation and its recorded decision belong to the owning call; nested calls never inherit approval or claims [src/invoker.ts:Invoker]
- Execution is deterministic replay: every `RunContext` call with a recorded result is answered from the stream [src/executor.ts:executeOnce]
- Run appends are serialized against one `expectedVersion`; `ConcurrencyError` retries the pass, `StaleRunOwnerError` never does [src/executor.ts:append]
- `execution.maxConcurrentRuns` must be 1–64 and capacity above one requires `resourceKeys` plus complete fenced outbox lease support [src/runtime.ts:startRuntime]
- Caller state writes land on `run-state-<id>`, never the run stream [src/fold.ts:runStateStream]
- Observations are keyed by tenant, world, and resource so equal resource strings in different worlds are distinct streams [src/fold.ts:observationStream]
- The runtime closes only a store it opened itself; an injected store belongs to its creator [src/runtime.ts:startRuntime]
- A run opened from an assignment records `assignment.issued` and `assignment.started` with `run.started`; every lifecycle write after start (interrupt, resume, spend, a budget breach and its stop, the terminal event) is an event on `run-assignment-<id>`, whose version is the lifecycle revision guarding it; the executor's terminal commit and `cancelRun` write both streams atomically, executor progress never touches the lifecycle stream; the view folds both by store position (read as a consistent pair), never a stored copy `[assignment.ts:foldAssignment]` `[fold.ts:assignmentControlStream]` `[service.ts:startRun]`
- An assignment id is issued to one run; a resume uses `resumeAssignment` on that run and is refused after the delegation link expired `[assignment.ts:createAssignmentService]`
- Executor progress for a bound run is fenced on the lifecycle revision: each progress commit carries a guard-only append on `run-assignment-<id>` at the version its own durable guard returned (never a shared variable), and every effect boundary is preceded by the same guard-only commit: a step callback, an external dispatch and the approved second call, an artifact write, a continuation open and a remote-offer take; a control that lands in between moves the version, the commit conflicts and the guard is taken again `[src/executor.ts:fence]`. Residual: an external call or artifact write already started, and agent code that never calls `ctx`, cannot be fenced and observe an interrupt only at their next boundary. A continuation opened before a budget stop is cancelled by finalization
- A cancel of a run whose assignment already failed (a budget stop not yet finalized, or a legacy failed crash state) finishes the run as `run.failed` with the recorded reason and aborts the local pass only after that is durable; the cancel is a no-op on an already-failed outcome, so the recorded failure is never overwritten. A legacy completed crash state (assignment ended on the run stream, run not terminal) is cancellable like any run: only `run.cancelled` is written and the assignment state stands. A legacy-failed run is finished without re-running the agent body; a legacy-completed one is re-run so its output is recomputed, so its effects outside recorded steps repeat (DEBT-034 class), and if that re-run fails the run is `failed` with an error saying the assignment had completed before the crash while the assignment view still reads completed. Open continuations of a terminal bound run are closed idempotently by the executor, `cancelRun` and recovery, so a cancel that failed after the terminal commit is retried `[src/service.ts:cancelRun]` `[src/assignment.ts:settleTerminalRun]`
- Two sequence meanings: `StoredEvent.streamSequence` is per stream (lifecycle events restart at 1 on `run-assignment-<id>`); the `streamSequence` handed to `outboxFor`, and so the observation's `source.sequence`, is run-wide (events of both streams so far); correlate events by `position`, not by sequence
- A cancel that cannot commit is refused as `unavailable` and leaves the run and its pass untouched; the local pass is aborted only after the cancel commits or the run is seen terminal `[src/service.ts:cancelRun]`
- A mixed-version fleet is unsupported for assignment runs: an older node never reads `run-assignment-<id>`, so it ignores a control a newer node accepted and can complete the run. Drain assignment runs, then upgrade every node; there is no version fence on the lifecycle stream
- A spend above a numeric limit records the overrun, then fails the run with `ASSIGNMENT_BUDGET_EXCEEDED` `[assignment.ts:createAssignmentService]`
- The RLM control stream `rlm-control/<parentRunId>` is the one authoritative record of an RLM invocation: `rlm.admitted` (invocation, attempt, child run id, request fingerprint, task key, protocol version), `rlm.child.started`, `rlm.dispatch.intended`, `rlm.cancel.requested`, `rlm.cancel.settled`, `rlm.revoked`, `rlm.parent.cancelled`, `rlm.outcome.accepted`. Generic run state (`state.changed`, snapshots, `updateState`) can never write it; every decision folds it and appends with a compare-and-set on its version, so a cancel, a revocation and a dispatch intent are totally ordered. Control events carry their identifiers in metadata, so a fold still attributes them (and still sees a revocation or a dispatch intent) after a payload is erased, and each event is caused by the one before it. The parent's `/rlm` state is no longer read, except as read-only history of invocations recorded before the stream existed `[rlm-control.ts:foldControl]`
- A child exists only for an admitted invocation: the service refuses any `startRun` of `agent.rlm` whose input is not exactly the admitted request of a parent in the caller's tenant (not cancelled, revoked or cancelled-at-the-invocation), takes the child's run id from the admission, and appends `rlm.child.started` in the same commit as `run.started` (which carries `rlmProtocol: 2`). The child re-checks the admission names its own run and request before it dispatches. The start must be made by the principal and with the case context the admission recorded, under the invocation's own correlation id. Modern children are found by the admitted run id, never by caller-suppliable correlation fields; the one exception is a pre-change binding that was still `pending-start` (no run id), which is found by its original correlation id and then verified (agent, invocation and parent) `[rlm-control.ts:admitChildStart]` `[service.ts:startRun]`
- Admission is one compare-and-set decision: the same invocationId must present the same attempt and the same request fingerprint (else refused), and a new invocationId for a task is admitted only when every predecessor attempt of that task has positive evidence of being finished: an accepted outcome, a settled cancellation (provider confirmed or nothing dispatched), or a terminal child with no dispatch intent, a dispatch step that refused before the provider was called (`rlm.dispatch.aborted`), or a terminal child whose recorded outcome is settled (an empty reconciliation records the outcome unsettled unless the provider is confirmed stopped). A requested but unsettled cancel, a terminal child after dispatch, and an admission without a child are not evidence. The task key is computed by the runtime from purpose, acceptance and context references; a caller-declared `contextDigest` is not trusted for it (DEBT-037) `[rlm.ts:createRlmComponent]`
- `agent.rlm` dispatches only for a child that carries the protocol marker: a history without it (even `run.started` alone) is a pre-change child and is only inspected, then reconciled. A dispatch intent is a compare-and-set append on the control stream after the child read no cancel, revocation or parent cancellation; if the stream moved, it decides again, so a cancel or revocation that commits first wins. The only window left is between that commit and the provider call, which is the provider's sticky-cancel obligation (`cancel` for a run the provider has not started must stick). A re-entry with an intent and no recorded result inspects the original invocation: a terminal view tied to the original `invocationId` (or, in the execution that made the call, an unnamed one) closes it, anything else parks on `ambiguous-invocation`; the decision to close is recorded with the view, so a replay never reopens it `[rlm.ts:createRlmAgent]`
- `rlm.cancel` records `rlm.cancel.requested` before it closes the child, cancels the child, reads the control stream (the fence makes "dispatched" final), asks the provider only if an intent exists, then records `rlm.cancel.settled` (a confirmed settlement is never replaced by a later failure); a failed or unsettled provider cancel is retried by a second call even on a terminal child. A cancelled parent appends `rlm.parent.cancelled` atomically with `run.cancelled`, so a child that has not dispatched refuses. Known debt DEBT-035: a parent's cancellation does not call `provider.cancel` for a child that already dispatched `[rlm.ts:createRlmComponent]` `[service.ts:cancelRun]`
- **BREAKING (#113):** `createRlmComponent` and `createRlmAgent` need `getService` and `getStore` (late-bound `() => runtime.service` and `() => runtime.store`); without them a dispatch fails closed. `revokeRlmGrant(runtime, caller, parentRunId, invocationId, reason)` takes the runtime and writes the control stream. A direct `startRun` of `agent.rlm` is refused. A pre-change child without the marker is never dispatched. An ordinary throw from `invoke` no longer fails the child: it is a lost response, inspected or parked; `RlmProviderRefusal` (the branded class, with a bounded `code`) declares that nothing ran. Mixed-version fleets are unsupported: an older node does not know the control stream `[rlm.ts:createRlmAgent]`
- Provider contract: `inspect(runId)` and `cancel(runId)` always receive the child run's id (`ctx.runId`), which a provider must record its state under. The provider receives a frozen facade of the run context (no prototype, no raw emitter): it cannot emit `rlm.outcome` or `rlm.dispatch.*`, write an `rlm.*` step or wait on `ambiguous:`/`rlm.` ids. Only a view accepted as this invocation's is ever written to a step; persisted error classes and cancel errors are allowlisted classes read once; the refusal code is validated at the record site `[rlm.ts:createRlmAgent]`
- Operator reconciliation must state a `result` or `failure`; the provider is asked again at that moment; a view that does not name the invocation is foreign (none of its spend or evidence is recorded); a `result` that contradicts a fresh tied `failed`, `timedOut` or `cancelled` view is refused (closed failed, disagreement recorded) unless the resolution carries `override: true`; the outcome and the child's output carry `reconciled: true`; the outcome is a recorded step (`rlm.outcome`, read by `rlm.inspect` only from that step for protocol-2 children) and `rlm.outcome.accepted` records it on the control stream `[rlm.ts:createRlmAgent]`
